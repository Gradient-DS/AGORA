# Research: Double Spoken Output Investigation

**Date**: 2026-03-23
**Researcher**: Claude
**Git Commit**: 37b4dd8
**Branch**: main
**Repository**: AGORA

## Research Question
The spoken output is coming back twice — once as an exact copy of the written text, and once as a properly generated spoken summary. What recent changes (last 4 days) caused this, and how can we fix it?

## Summary

**The recent commits (last 4 days) do NOT introduce double spoken.** After exhaustive code tracing through every `send_spoken_text_*` call path in the orchestrator, there is no server-side code path in `server-langgraph` that sends spoken text twice for a normal message. The issue is most likely caused by **how the frontend processes spoken data from two separate sources** (REST history endpoint + WebSocket events), or by a subtle edge case not visible in static analysis.

### Commits in Scope (Last 4 Days: March 19-23)

| Commit | Date | Change | Impact on Spoken |
|--------|------|--------|------------------|
| `fe668a6` | Mar 22 | Regex cleanup of clarification spoken text | Modified content of existing send, did NOT add new send |
| `2bce6b7` | Mar 16 | Changed spoken prompt (no "Samenvatting:" label) | Prompt-only change, no flow change |

Neither commit adds a new `send_spoken_text_content` call or changes the spoken event flow.

## Detailed Findings

### 1. All Spoken Send Paths in `_stream_response()` (Mutually Exclusive)

I traced every call to `send_spoken_text_start` and `send_spoken_text_content` in the orchestrator:

| # | Location | When it fires | Mode |
|---|----------|--------------|------|
| 1 | `_generate_spoken()` (line 723, 730) | Parallel task in summarize mode | summarize only |
| 2 | Main loop (line 904, 915) | Duplicates written chunks to spoken | dictate only |
| 3 | Clarification handler (line 1222, 1239) | Graph interrupted with clarification | interrupt only |
| 4 | Listen mode handler (line 1276, 1279) | `final_spoken` from graph state | listen mode only |

**These are mutually exclusive:**
- Path 1 vs 2: Guarded by `spoken_mode == "summarize"` vs `spoken_mode == "dictate"` (set once, line 798)
- Path 1 vs 3: Parallel task is cancelled on interrupt (`spoken_task.cancel()`, line 1315)
- Path 1 vs 4: Listen mode sets `message_started = False`, so path 4 only fires when path 1 never started
- Fallback sequential generation (line 1344) is `elif` with path 1, so they can't both run

### 2. No Double `send_spoken_text_start` in Summarize Mode

In summarize mode for a normal response:
- `_generate_spoken()` calls `send_spoken_text_start` once (line 723, guarded by `spoken_started` flag)
- Main loop does NOT call `send_spoken_text_start` (line 901 requires `spoken_mode == "dictate"`)
- `send_spoken_text_end` is called once at line 1386

### 3. Architecture Change Context (March 10)

The `1723a67` commit (March 10, outside the 4-day scope) made a significant architecture change:

**Before** (pre-March 10): Two graph nodes (`generate_written`, `generate_spoken`) ran in parallel via `Send` API, both as LLM calls within the graph. Written+spoken chunks came through `astream_events`.

**After** (current): Agent's response IS the written text (streamed directly from agent nodes). Spoken is generated by `_generate_spoken()` as an `asyncio.create_task()` running outside the graph.

This change is clean — no leftover `generate_spoken` node handling in the streaming loop.

### 4. Potential Root Cause: Frontend Dual-Source Conflict

The server provides spoken text through **two independent channels**:

1. **WebSocket events** (real-time): `agora:spoken_text_start/content/end` custom events during streaming
2. **REST history endpoint** (`/sessions/{id}/history`): Each assistant message includes a `spoken_text` field (persisted at line 1367 after generation)

If the frontend uses BOTH sources for the same message — e.g., receiving real-time spoken events AND reading `spoken_text` from a history reload — the user would see spoken twice: once as the properly generated summary (from events) and potentially once from the stored `spoken_text` in history.

### 5. The `spoken_text` Persistence Flow

After spoken generation completes:
```python
# Line 1356-1377: Persists spoken_text in AIMessage additional_kwargs
updated_kwargs["spoken_text"] = spoken_content
await self.graph.aupdate_state(config, {"messages": [updated_msg]})
```

Then in history endpoint:
```python
# Line 1496: Returns spoken_text in history response
spoken_text = msg.additional_kwargs.get("spoken_text")
# Line 1509/1533/1541: Included in every assistant message
{"role": "assistant", "content": "...", "spoken_text": spoken_text}
```

## Suggestions

### Investigation Step 1: Check the Frontend (Most Likely Cause)
Check `HAI/src/hooks/useTTS.ts` and the WebSocket handler for how spoken text is accumulated. If the frontend:
- Loads `spoken_text` from history REST response for the latest message
- AND receives real-time `agora:spoken_text_content` WebSocket events
...that would explain the double spoken (one = written text from history content, one = properly generated spoken from events).

### Investigation Step 2: Add Server-Side Logging
Add a counter or debug log to track how many `agora:spoken_text_content` events are sent per message_id:

```python
# In ag_ui_handler.py send_spoken_text_content
async def send_spoken_text_content(self, message_id: str, delta: str) -> None:
    if not delta:
        return
    log.debug(f"SPOKEN_CONTENT event for {message_id}: {len(delta)} chars")
    # ... existing code
```

### Investigation Step 3: If the Issue IS Server-Side
If logging confirms double sends, the most likely edge case would be:
- A race condition where `_generate_spoken()` sends content AND the graph state `final_spoken` also gets sent
- Check if `final_spoken` is being set by a graph node when it shouldn't be

### Possible Server-Side Fix (Preventive)
Add a guard in the protocol handler to prevent double `spoken_text_start`:

```python
# In AGUIProtocolHandler
def __init__(self, ...):
    self._spoken_started_for: set[str] = set()

async def send_spoken_text_start(self, message_id: str, role: str = "assistant") -> None:
    if message_id in self._spoken_started_for:
        log.warning(f"DUPLICATE spoken_text_start for {message_id}, skipping")
        return
    self._spoken_started_for.add(message_id)
    # ... existing code
```
