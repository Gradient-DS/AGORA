# Research: Improving TTS Pronunciation of Large Numbers and Complex Codes

**Date**: 2026-02-22T15:00:00+01:00
**Researcher**: claude
**Git Commit**: ac8982c
**Branch**: main
**Repository**: Gradient-DS/AGORA

## Research Question

Models struggle with pronouncing large numbers in spoken TTS output. Two proposed solutions:
1. Write out numbers one by one in text (e.g., "twee drie zes negen")
2. For long/complex numbers and codes, don't pronounce them — refer the user to the chat instead

## Summary

This is a **prompt-only change** — no code modifications needed. The spoken text is generated by a separate LLM call using `SPOKEN_AGENT_PROMPTS` defined in `agent_definitions.py` (both orchestrators). These prompts already contain some number-handling instructions, but they're incomplete and inconsistent across agents. The fix requires updating 8 prompt blocks across 2 files.

## Detailed Findings

### How Spoken Text Works (Architecture)

The system uses a **dual-channel architecture**:
1. Written text is generated by the main agent with the full system prompt
2. Spoken text is generated **in parallel** by a separate LLM call using `SPOKEN_AGENT_PROMPTS`
3. Both receive the same conversation history but different system prompts
4. The frontend receives both streams and sends spoken text to ElevenLabs TTS

Two modes exist (per-user preference `spoken_text_type`):
- **`summarize`** (default): Separate LLM call with spoken-specific prompt → this is where changes matter
- **`dictate`**: Written text is duplicated to spoken channel → no prompt control possible

### Current State of Number Handling in Spoken Prompts

| Agent | Current number instructions | Gap |
|-------|---------------------------|-----|
| `general-agent` (langgraph) | Abbreviations only: KVK, NVWA, °C | No number handling at all |
| `general-agent` (openai) | Same as above | Same gap |
| `regulation-agent` (both) | Good: `'22°C' → 'tweeëntwintig graden Celsius'`, `'EU 852/2004' → 'Europese Unie verordening...'`, `'Art. 5' → 'artikel vijf'` | Covers regulation-specific numbers but not general numbers |
| `reporting-agent` (langgraph) | Explicit: "Zeg alleen rapport ID en ontvanger" | **Actively instructs to SAY the report ID** which is exactly the problem |
| `reporting-agent` (openai) | Less specific, just "Maximaal 2 zinnen" | No number guidance |
| `history-agent` (both) | Only: `'KVK' → 'Kamer van Koophandel'` | No number handling |

### What Needs to Change

Add two categories of instructions to all `SPOKEN_AGENT_PROMPTS`:

**Category 1: Digit-by-digit pronunciation for long numbers**
```
- Schrijf lange nummers cijfer voor cijfer uit met spaties:
  * '12345678' → 'één twee drie vier vijf zes zeven acht'
  * Postcode: '1234AB' → 'één twee drie vier A B'
```

**Category 2: Omit complex codes entirely, refer to chat**
```
- Noem GEEN complexe codes, rapport-IDs, referentienummers of URLs
- Verwijs naar de chat voor details:
  * In plaats van 'Rapport HAP-2842A-2 is aangemaakt' → 'Het rapport is aangemaakt, de details staan in de chat'
  * In plaats van 'KVK nummer 12345678' → 'Ik heb het bedrijf gevonden, de details staan in de chat'
```

The choice between category 1 and 2 depends on context:
- **Short numbers** (phone, KVK 8-digit): could use digit-by-digit
- **Complex codes** (report IDs like `HAP-20251218-39A787FB`, email addresses, URLs): should be omitted entirely

### Reporting Agent: Special Attention

The langgraph reporting-agent spoken prompt currently says:
```
2. Bij rapport generatie: Zeg alleen rapport ID en ontvanger.
   Voorbeeld: 'Rapport INS-2024-AB12CD is aangemaakt en verzonden naar jan@bedrijf.nl.'
```

This should become something like:
```
2. Bij rapport generatie: Bevestig kort dat het rapport is aangemaakt.
   Voorbeeld: 'Het rapport is aangemaakt en verzonden. De details en download links staan in de chat.'
```

### Dictate Mode Consideration

In `dictate` mode, the written text is duplicated verbatim to the spoken channel — no separate LLM call is made. This means prompt changes will **not** affect dictate mode users. If dictate mode users also struggle with number pronunciation, that would require either:
- Post-processing the written text before sending to TTS (code change)
- Switching dictate users to summarize mode (config change)
- Or accepting that dictate mode inherently reads everything as-is

## Architecture Insights

- The dual-channel system is well-designed for this exact type of change — spoken prompts can be independently tuned without affecting written output
- The `summarize` mode is the correct lever for controlling TTS pronunciation
- Report IDs are generated in `session_manager.py` as `HAP-{date}-{uuid}` (e.g., `HAP-20251218-39A787FB`) — these are definitively too complex for TTS
- The existing spoken prompts already demonstrate the pattern (regulation-agent has number rules), it just needs to be applied consistently

## Effort Estimate

- **Scope**: Prompt-only change, 2 files, 8 prompt blocks
- **Risk**: Low — spoken prompts are independent from written output
- **Testing**: Manual testing with TTS enabled, verify numbers are handled correctly
- **Consideration**: Should create a shared "TTS rules" block to avoid duplicating instructions across all 4 agents — currently each agent prompt is independent

## Open Questions

1. **Which approach per context?** Should KVK numbers (8 digits) be spoken digit-by-digit or also omitted? The user's examples suggest option 2 (refer to chat) is preferred for most cases.
2. **Email addresses**: Should email addresses be spoken or omitted? The user's example keeps the email in the spoken output. ElevenLabs may handle simple email addresses acceptably.
3. **Dictate mode**: Should dictate mode users also get this treatment? That would require a code change (post-processing).
4. **Shared prompt block**: Should the number/code rules be extracted into a shared constant that's prepended to all spoken prompts, to avoid duplication?
