# Sequential Spoken Generation from Written Text — Implementation Plan

## Overview

Change spoken text generation from parallel (independent LLM call) to sequential (derived from written text). The spoken LLM will receive the completed written response as explicit context, ensuring spoken output is always a faithful summary of written — never divergent.

Scoped to **server-langgraph** only.

## Current State Analysis

Today, written and spoken text are generated by **two independent, parallel LLM calls** with different inputs:

- **Written**: Produced by the agent node inside the LangGraph graph. Gets full agent instructions, tool calls, and ToolMessages.
- **Spoken**: Started as `asyncio.create_task` on the first written chunk (`orchestrator.py:861`). Gets a snapshot of messages taken **before** the graph runs, tool results as injected text, and a short TTS-optimized system prompt. Never sees the written response.

This causes divergence: the spoken LLM independently interprets the conversation and can reach a completely different conclusion (e.g., written asks for postcode, spoken says "I'll look it up").

### Key Discoveries:
- Spoken context snapshot is taken pre-graph at `orchestrator.py:813`
- Parallel task created at `orchestrator.py:879` on first text chunk
- `_build_spoken_messages()` at `orchestrator.py:649` strips tool calls/ToolMessages
- Spoken prompts in `agent_definitions.py:350-441` instruct "independently answer"
- A sequential fallback path already exists at `orchestrator.py:1328-1354`
- Dictate mode (line 897-917) and clarification handler (line 1208-1246) are unaffected
- Listen mode (line 1274-1282) uses `final_spoken` from graph state — unaffected
- Test file: `tests/integration/test_dual_channel_spoken.py`

## Desired End State

After this plan:
1. Spoken text is generated **after** the written response completes
2. The spoken LLM receives the full written text as explicit context
3. Spoken output is always a faithful TTS-friendly summary of the written text
4. Dictate mode, clarification interrupts, and listen mode continue working unchanged
5. Tests updated to reflect sequential flow

### How to verify:
- Send "haal de gegevens op van restaurant bella rosa" — spoken should summarize the written response (e.g., "Ik heb je postcode en huisnummer nodig"), not independently answer
- Dictate mode still duplicates written to spoken channel
- Clarification interrupts still produce spoken inline
- All tests pass: `cd server-langgraph && pytest tests/integration/test_dual_channel_spoken.py`

## What We're NOT Doing

- Changing `server-openai` (out of scope per user request)
- Changing dictate mode behavior
- Changing clarification/interrupt spoken handling
- Changing listen mode spoken handling
- Changing the spoken LLM model or provider chain
- Optimizing latency (we accept the sequential cost)

## Implementation Approach

The change is concentrated in two files:
1. `orchestrator.py` — remove parallel path, add sequential spoken after graph
2. `agent_definitions.py` — update spoken prompts to "summarize this written response"

We keep `_generate_spoken()` and `_build_spoken_messages()` as utilities but change how they're called and what context they receive.

Replace lines 1311-1354 (the `if spoken_task:` block and the `elif` fallback) with a single sequential block:

```python
# Generate spoken text sequentially from the completed written response
spoken_content = ""
if (
    spoken_mode == "summarize"
    and not graph_was_interrupted
    and not listen_mode_response
    and message_started
):
    try:
        written_text = "".join(full_response)
        state_messages = (
            final_state.values.get("messages", [])
            if final_state and final_state.values
            else []
        )
        if state_messages:
            spoken_messages = self._build_spoken_messages(state_messages)
            spoken_content = await self._generate_spoken(
                agent_id=current_agent_id,
                messages=spoken_messages,
                message_id=message_id,
                protocol_handler=protocol_handler,
                written_text=written_text,
            )
            spoken_message_started = spoken_message_started or bool(
                spoken_content
            )
    except Exception as e:
        log.warning(f"Failed to generate spoken text: {e}", exc_info=True)
```

## Performance Considerations

- **Added latency**: Spoken generation starts only after written completes (~2-3s delay). Total time = written streaming + spoken generation (was: max of both).
- **No streaming overlap**: The spoken channel will be silent while written streams, then spoken streams after. Frontend should handle this gracefully (it already does for the fallback sequential path).
- **LLM call efficiency**: The spoken LLM now receives the written text directly instead of independently re-deriving it. This may actually produce shorter/faster spoken output since it's summarizing rather than answering from scratch.
